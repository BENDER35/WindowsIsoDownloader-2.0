# Technical Guide — Windows 10 ISO Downloader

This document explains **how the tool works internally**, its architecture, the
configuration model and the reasoning behind the main implementation decisions.
It targets developers who need to maintain, extend or audit the project.

> Language: [English](TECHNICAL_GUIDE.md) | [Español](TECHNICAL_GUIDE.es.md)
> Main documentation: [readme.md](../readme.md)

## 1. Purpose and context

Microsoft publishes the Windows 10 and Windows 11 ISOs only through an
interactive web page. The download link is a short-lived, signed URL that is
generated by the page itself after the user selects an edition and a language.
There is no official public API for this.

This tool automates that browser interaction with **Playwright for .NET** and
then downloads the generated URL with `HttpClient`. The result is a single,
repeatable command that a build pipeline (for example
[`tiny11builder`](https://github.com/ntdevlabs/tiny11builder)) can call to fetch
the ISO.

The repository ships a `config.json` that targets the **Windows 10
(multi-edition ISO)** edition (`2618`, at `/software-download/windows10ISO`).
Because the workflow is pure data, the same binary can fetch Windows 11
(edition `3813`) or another edition by editing the configuration.

## 4. Configuration model

`config.json` is deserialized into the classes in `Config.cs`:

```
Config
 ├── DownloadFolder : string
 ├── DownloadFilename : string
 └── Actions : List<BrowserAction>
        ├── Order : int
        ├── Kind : string            // Goto | SelectOption | Click | QuerySelector
        ├── WaitBeforeAction : int?  // milliseconds
        └── Parameters : BrowserActionParameters
               ├── Url : string?
               ├── Selector : string?
               └── Values : string?
```

`JsonSerializerOptions` enables `PropertyNameCaseInsensitive`,
`ReadCommentHandling = Skip` and `AllowTrailingCommas`, so the file is tolerant
to casing, comments and trailing commas. This makes it easier to hand-edit.

The actions are sorted by `Order` and interpreted by a small interpreter
(`RunActionsAsync`) whose action set is intentionally minimal:

| `Kind` | Effect on the page |
| --- | --- |
| `Goto` | `page.GotoAsync(url)` |
| `SelectOption` | `page.SelectOptionAsync(selector, values)` |
| `Click` | `page.ClickAsync(selector)` |
| `QuerySelector` | `page.QuerySelectorAsync(selector)`, storing the handle |

Keeping the workflow in data (rather than hard-coded) is the core design
decision: when Microsoft renumbers an option it is a one-line change in
`config.json`.

## 5. Execution flow

```
Start
  │
  ├─ 1. Set console output encoding to UTF-8 (progress bar glyphs)      [best effort]
  ├─ 2. Read and deserialize config.json  ── invalid? ──► exit -1
  ├─ 3. Validate config (folder, filename, non-empty actions)
  ├─ 4. Create DownloadFolder; compute absolute output path
  ├─ 5. Install Playwright browser dependencies (firefox)  ── fail? ──► exit -1
  ├─ 6. Playwright.CreateAsync() + Firefox.LaunchAsync()
  │
  ├─ 7. Retry loop (up to 3 attempts, fresh browser context each time):
  │        a. New context (Locale = en-US) + new page
  │        b. RunActionsAsync(page, actions)   → maybe a QuerySelector handle
  │        c. ResolveIsoUrlAsync(page, handle):
  │              - poll for every `a[href*=".iso"]` link (10 tries / 1 s)
  │              - prefer the 64-bit image when several are offered
  │              - otherwise use the handle's href, then the first link
  │        d. If a link was found → stop retrying
  │           else wait 5 s and retry
  │
  ├─ 8. If no link → exit -1
  ├─ 9. HttpClient.DownloadAsync(isoUrl, FileStream, progress)  → writes the ISO
  ├─ 10. Print success and exit 0
```

### 5.1 Why the retry loop exists

Microsoft's download connector is protected by an internal anti-bot mechanism
that answers with:

```json
{"Errors":[{"Key":"ErrorSettings.SentinelReject",
           "Value":"Sentinel marked this request as rejected.","Type":8}]}
```

when it distrusts a browser session (common with automated or repeated access).
A brand-new browser context usually gets a fresh, accepted session, so the tool
retries up to three times. The failure is not caused by the code; it is a
server-side decision, and the tool degrades gracefully with a clear message.

### 5.2 Link resolution

The historically fragile point was the CSS selector for the download button
(`#card-info-content .button`). Microsoft's markup changed the class, so the
code now:

1. Polls the page for every anchor whose `href` contains `.iso`, for a few
   seconds, because the download section renders asynchronously.
2. When the page offers more than one image, **prefers the 64-bit one**: Windows
   10 publishes a 32-bit (`..._x32v1.iso`) and a 64-bit (`..._x64v1.iso`) image,
   so the code selects the link whose URL contains `x64`.
3. If no `.iso` link contains `x64`, it falls back to the element of the
   configured `QuerySelector` action, and finally to the first `.iso` link.

The page returns the links as a JSON array string that the code deserializes with
`System.Text.Json` (Playwright's own `EvaluateAsync<T>` deserializer does not
round-trip a `List<string>` reliably). The final URL is validated
(`Contains(".iso")`) before downloading.

## 6. Downloading with progress

`HttpClientExtensions.DownloadAsync` requests the URL with
`HttpCompletionOption.ResponseHeadersRead` so the response is streamed instead
of buffered, then delegates to `StreamExtensions.CopyToAsync`. That method
copies the stream in 80 KiB chunks and reports the total number of bytes read
through an `IProgress<long>`. `DownloadAsync` converts bytes into a `0..1`
ratio and reports it as `IProgress<float>`, which the program renders as a
100-column bar.

The `Progress<T>` callbacks are dispatched on the captured synchronization
context; because the value is a simple float and the console writes are cheap,
this is sufficient. The progress renderer guards `Console.SetCursorPosition`
with `!Console.IsOutputRedirected` and a `try/catch (IOException)` so redirected
output (CI logs, files) does not crash the tool.

## 7. Cross-platform notes

The original project targeted .NET 6 and assumed Windows (`"DownloadFolder":
"C:\\"`). The following changes make it work on Linux/macOS too:

- **Target framework** raised to `net10.0`.
- **Playwright** upgraded to a current version with up-to-date browser builds
  for Linux.
- **`config.json` default folder** changed to `"."` (relative to the working
  directory) instead of `C:\`.
- **Path handling** uses `Path.Combine` + `Path.GetFullPath`, so both `/` and
  `\` paths work.
- **Console output** sets UTF-8 encoding so the `█`/`░` glyphs render, and
  guards cursor repositioning when output is redirected.
- **Error messages** mention the Linux `playwright install-deps firefox` step.

The Firefox binary and its system dependencies are the only OS-specific
requirement. On .NET, Playwright ships platform-specific drivers for Windows,
Linux and macOS automatically via the NuGet package.

## 8. Building, running and publishing

```bash
# Development build
dotnet build -c Release

# Framework-dependent run
dotnet bin/Release/net10.0/WindowsIsoDownloader.dll

# Self-contained single-folder publish (example: Linux x64)
dotnet publish -c Release -r linux-x64 --self-contained true

# Self-contained single-file publish
dotnet publish -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true
```

`config.json` is copied to the output folder (`CopyToOutputDirectory=Always`).
At runtime the tool first looks for `config.json` next to the executable and
falls back to the current working directory.

### 8.1 32-bit (x86) and ARM support

The project is `AnyCPU` (`PlatformTarget=AnyCPU`, `Prefer32Bit=false`) and the
C# code is pointer-size agnostic: sizes and offsets use `long`
(`ContentLength`, total bytes read) and the file is written through a
`FileStream`, so an ISO larger than 2 GiB is not truncated by a 32-bit process.

```bash
# 32-bit x86 Windows
dotnet publish -c Release -r win-x86 --self-contained true -p:PlaywrightPlatform=win

# 32-bit ARM Linux
dotnet publish -c Release -r linux-arm --self-contained true
```

`Microsoft.Playwright.targets` selects the driver folder from the active
`RuntimeIdentifier`. `win-x86` and `linux-arm` are not recognized by that target,
and an unrecognized RID makes it copy **every** platform's driver (~575 MB).
Passing `-p:PlaywrightPlatform=win` pins the copy step to `win32_x64`, the only
driver that exists for Windows, and keeps the 32-bit package small. This is also
why the `.csproj` deliberately does **not** declare `RuntimeIdentifiers`
(declaring it would trigger the same fallback on a plain build).

What can actually run is limited by the browser engine, not by the managed code:

| Target | Builds? | Runs? |
| --- | --- | --- |
| `win-x64` | Yes | Yes |
| `win-x86` | Yes (add `-p:PlaywrightPlatform=win`) | On 64-bit Windows only: the 32-bit process starts Playwright's bundled 64-bit `node.exe`. A 32-bit-only Windows cannot run it. |
| `linux-x64` | Yes | Yes |
| `linux-arm64` | Yes | Yes |
| `linux-arm` | Yes | No: Playwright ships the `linux-x64` driver for non-arm64 Linux, so the browser cannot start. |
| `linux-x86` | No | No: .NET 10 has no 32-bit x86 Linux apphost (`NETSDK1084`). |

`Driver.GetPath` in `Microsoft.Playwright` hard-codes `win32_x64` on Windows and
picks `linux-arm64` vs `linux-x64` on Linux, which is the root cause of the
runtime limitations above.

## 10. Maintenance checklist

If the tool stops finding the link:

1. Open the [download page](https://www.microsoft.com/en-us/software-download/windows10ISO)
   and inspect `#product-edition`; update `Order: 2` `Values`.
2. Confirm the edition, then inspect `#product-languages`; update `Order: 4`
   `Values` with the full JSON value of your language.
3. Verify the final selector (default `#card-info-content a`) against the
   generated download anchor.
4. If the page was restructured, adjust the sequence of actions/selectors.
5. Bump the Playwright NuGet package periodically so browser builds stay
   current and pass the site's compatibility checks.

## 11. Language reference

The `Values` of the `SelectOption` action with `Order: 4` is the JSON string
`{"id":"<skuId>","language":"<name>"}` taken from the `#product-languages`

connector's SKU list
(`getskuinformationbyproductedition?profile=606624d44113&productEditionId=2618`),

## 12. Windows 10 support lifecycle and Windows Update certificate rotation

Windows 10 reached end of support on **October 14, 2025**. From then on only the
Extended Security Updates (ESU) program delivers security fixes:

| Stage | Ends | Applies to |
| --- | --- | --- |
| Ordinary support | October 14, 2025 | Everyone |
| ESU – Year 1 | October 13, 2026 | Commercial / educational |
| ESU – Year 2 | October 12, 2027 | Consumers (end of consumer ESU); Year 2 for commercial |
| ESU – Year 3 | October 10, 2028 | Commercial / educational only |

Windows Update itself is also affected by the **2027 certificate rotation**. The
service certificates expire and their replacements must be installed before
**May 17, 2027** or **June 19, 2027** (depending on the product). Systems that
cannot receive them — **Windows 7, Windows 8 / 8.1, Windows 10 without ESU** and
the out-of-support Windows Server releases — will be unable to connect to
Windows Update. This is a server-side certificate rotation and is independent of
this tool; the only remediation is a supported OS or a Windows 10 installation
with ESU that keeps installing the monthly update.

References:

- End of support and ESU:
  <https://www.microsoft.com/en-us/windows/extended-security-updates>
- Certificate rotation announcement:
  <https://techcommunity.microsoft.com/blog/windows-itpro-blog/prepare-for-windows-update-certificate-rotation-in-2027/4562463>

## 13. Security and legal notes

- The tool downloads only Microsoft's public, official ISOs; it does not bypass
  licensing.
- The signed download URLs expire; they are used immediately and never stored.
- Never commit a GitHub Personal Access Token into source files; use a
  credential helper or environment variable instead.
